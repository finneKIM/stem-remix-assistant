# librosa.beat.beat_track가 start_bpm 없이 호출되면 템포를 2배로 측정한다

## 상황

생성 음원의 음질 저하 원인을 찾는 과정에서, 코덱(EnCodec)이 음질을 떨어뜨리는지 확인하려고 원곡을 인코딩 후 디코딩한 왕복 음원을 만들어 지표를 측정했다. 원곡의 BPM은 선행 분석에서 89로 확정된 상태였다.

## 에러

**예외가 발생하지 않는다.** 함수가 정상 반환하고, 반환된 값이 틀렸다.

측정 결과다.

```
파일                flatness   8kHz+     BPM
원곡                0.00679    0.0579    89.0
코덱 왕복           0.00451    0.0472    178.6
```

flatness와 고역 에너지는 코덱 왕복이 원곡보다 **낮게**(= 더 좋게) 나왔는데, BPM만 89에서 178.6으로 튀었다. 178.6은 89의 약 2배다.

이 수치만 보고 "코덱이 템포를 망가뜨린다"는 결론으로 갈 뻔했다. 코덱은 파형을 재구성하므로 템포를 바꿀 이유가 없는데, 측정값이 그렇게 나왔다.

## 원인

`librosa.beat.beat_track`은 onset envelope의 자기상관으로 템포를 추정하고, 후보 중 하나를 고를 때 **사전 분포(prior)의 중심값**을 쓴다. 그 중심값의 기본값이 120 BPM이다.

89 BPM 곡의 비트 간격은 그 2배(178)에서도 자기상관 피크가 생긴다. 2분음표 간격과 4분음표 간격이 둘 다 주기적이기 때문이다. 이 둘 중 어느 쪽을 고를지는 사전 분포가 결정하고, 기본값 120에 더 가까운 쪽은 **89가 아니라 178**이다.

이것이 템포 추정의 고전적 실패 유형인 **옥타브 오류(octave error)** 다. 2배 또는 절반으로 어긋나고, 중간값은 나오지 않는다. 그래서 틀린 값도 "그럴듯한 템포"로 보인다.

코덱 왕복 음원에서만 튄 이유는 코덱이 고역 성분을 깎아내면서 타격음의 onset 선명도가 달라져, 두 후보의 자기상관 세기 순위가 뒤집혔기 때문으로 보인다. 즉 **코덱이 템포를 바꾼 것이 아니라, 추정기의 후보 선택을 뒤집은 것**이다.

## 해결

목표 BPM을 알고 있다면 `start_bpm`으로 사전 분포의 중심을 옮긴다.

```python
import numpy as np
import librosa

def measure_tempo(path, sr=32000, hint_bpm=None):
    y, sr = librosa.load(path, sr=sr, mono=True)
    kw = {"start_bpm": hint_bpm} if hint_bpm else {}
    tempo, _ = librosa.beat.beat_track(y=y, sr=sr, **kw)
    return float(np.atleast_1d(tempo)[0])
```

측정 함수의 인자로 올려서 호출할 때마다 넘기도록 강제한다.

```python
print(measure_tempo("codec_roundtrip.wav"))                 # 178.6  (틀림)
print(measure_tempo("codec_roundtrip.wav", hint_bpm=89))    #  89.0  (맞음)
```

### 힌트가 정상 케이스를 왜곡하지 않는지 함께 확인한다

힌트를 넣는 것은 사전 분포를 조작하는 것이므로, **원래 맞게 나오던 파일의 값을 끌어당기지 않는지** 확인해야 한다. 힌트를 믿고 쓰기 전에 전 파일을 두 방식으로 재측정해 대조한다.

```python
for p in files:
    a = measure_tempo(p)
    b = measure_tempo(p, hint_bpm=89)
    flag = "" if abs(a - b) < 2 else "  <- 힌트로 값이 바뀜"
    print(f"{p:50} 힌트없음 {a:6.1f}   힌트있음 {b:6.1f}{flag}")
```

바뀐 파일만 따로 보고, 바뀐 방향이 옥타브 관계(2배/절반)인지 확인한다. 옥타브 관계가 아니라 조금씩 끌려오는 것이라면 힌트가 과하게 작용하는 것이므로 쓰지 않는다.

### 목표 BPM을 모르는 경우

힌트를 쓸 수 없으므로, 추정값과 그 2배·절반을 모두 후보로 두고 다른 근거로 고른다. onset 간격 히스토그램을 직접 보거나, 비트 그리드를 음원에 겹쳐 들어보는 방법이 있다. **단일 추정값을 그대로 지표에 넣지 않는다.**

## 주의사항

힌트는 **측정값이 아니라 사전 지식을 주입하는 것**이다. 따라서 힌트를 넣어 얻은 BPM은 "모델이 이 템포로 연주했다"의 증거로 쓸 때 주의해야 한다. 생성물의 템포가 목표에서 크게 벗어났는지 보려는 것이 목적이라면, 힌트가 그 벗어남을 가려버릴 수 있다.

이 사례에서는 목표 BPM이 외부에서 확정된 값이었고, 확인하려는 것은 "코덱 전후로 템포가 유지되는가"였으므로 힌트가 적절했다. 반대로 "모델이 지시한 BPM을 따랐는가"를 재려면 힌트 없이 측정하고 옥타브 후보를 수동으로 확인하는 쪽이 맞다.

## 배운 점 / Development Way

예외를 던지지 않고 **그럴듯한 틀린 값을 반환하는 함수**가 가장 위험하다. 예외는 눈에 보이지만 틀린 숫자는 그대로 지표에 들어가고, 거기서 내린 결론은 그 다음 작업 전체의 전제가 된다. 분석 함수를 쓸 때는 반환값이 틀릴 수 있는 방식을 먼저 알아 두고, 그 방식에 맞는 검증을 붙인다. 템포 추정이라면 옥타브, 피치 추정이라면 하모닉, 키 추정이라면 상대 단조·장조가 그런 유형이다.

**이미 알고 있는 값으로 측정 함수를 먼저 검증한다.** 이번에는 원곡 BPM이 확정돼 있었기 때문에 178.6이 이상하다는 것을 알 수 있었다. 알려진 값이 하나도 없는 상태로 측정을 시작하면, 틀린 값과 맞는 값을 구별할 기준이 없다. 측정 파이프라인을 만들 때는 정답을 아는 입력 하나를 고정 테스트로 넣어 둔다.

여러 지표를 동시에 보는 것이 이 오류를 잡았다. flatness와 고역 에너지가 "코덱 왕복이 더 좋다"고 일관되게 말하는데 BPM만 반대 방향으로 튀었기 때문에, 코덱을 의심하는 대신 **측정 쪽을 의심할 수 있었다.** 지표가 하나였다면 그 하나를 믿었을 것이다. 지표를 복수로 두는 이유는 대상을 여러 각도로 보는 것만이 아니라, **측정 자체의 고장을 교차로 검출하기 위한 것**이기도 하다.

파라미터 기본값이 분포의 중심을 정하는 함수라면, 그 기본값이 내 데이터에 맞는지 확인한다. 120 BPM은 대중음악의 중앙값으로는 합리적인 기본값이고, 그래서 라이브러리 잘못이 아니다. 다만 89 BPM 곡을 다루는 쪽에서는 그 기본값이 틀린 전제이고, **기본값이 전제를 담고 있다는 사실 자체를 모르면 조정할 생각도 하지 못한다.**
