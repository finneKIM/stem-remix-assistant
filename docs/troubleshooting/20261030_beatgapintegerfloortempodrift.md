# 비트 조건을 프레임 인덱스로 만들면 정수 내림 때문에 지시한 BPM과 다르게 연주된다

## 상황

MusiConGen에 BPM 89를 조건으로 넣어 생성한 결과를 측정했는데, 템포가 일관되게 90~91 사이로 나왔다. 처음에는 모델이 조건을 제대로 따르지 않는 것으로 의심했다.

## 에러

**에러가 없다.** 지시한 값과 결과값이 다를 뿐이다.

```
목표 BPM   89
측정 BPM   91.5   (cfg_coef 1.5)
측정 BPM   96.2   (cfg_coef 3.0)
```

두 측정값이 모두 89보다 크다는 것, 특히 작은 쪽이 91.5로 **일정하게** 치우쳐 있다는 것이 단서였다. 모델이 조건을 무시하면 값이 무작위로 흩어질 텐데, 한 방향으로 쏠려 있었다.

## 원인

비트 조건을 합성하는 코드가 비트 간격을 **프레임 개수(정수)** 로 계산한다.

```python
fs = self.sample_rate / 640          # 32000 / 640 = 50 frames per second
beat = np.zeros(int(fs * self.duration))
beat_gap = int(60 / bpm * fs)        # <- 여기
beat[::beat_gap] = 1
bar = np.zeros(int(fs * self.duration))
bar[::beat_gap * meter] = 1
kernel = np.array([0.05, 0.1, 0.3, 0.9, 0.3, 0.1, 0.05])
beat = np.convolve(beat, kernel, 'same') + bar
```

조건 시퀀스의 해상도는 초당 50프레임이다. 89 BPM의 비트 간격을 프레임으로 환산하면

```
60 / 89 * 50 = 33.7078...
```

`int()`가 소수점을 버려 **33프레임**이 된다. 33프레임 간격의 실효 BPM은

```
50 / 33 * 60 = 90.909...
```

즉 89를 넣으면 조건 자체가 **90.91 BPM의 비트 그리드**로 만들어진다. 모델은 지시를 충실히 따랐고, 지시가 90.91이었다.

이것은 버그가 아니라 **양자화(quantization)의 필연적 결과**다. 연속값인 템포를 50fps 정수 격자에 올리면 격자가 표현할 수 있는 템포만 남는다. 50fps에서 표현 가능한 BPM은 `50/n*60` 꼴의 이산값이다.

```
n=33 → 90.91
n=34 → 88.24
n=35 → 85.71
```

89는 이 목록에 없다. 89에 가장 가까운 표현 가능한 값이 88.24(n=34)와 90.91(n=33)이고, `int()`는 항상 내림이므로 33이 선택되어 **위쪽**으로 치우친다.

`cfg_coef` 3.0에서 96.2가 나온 것은 별개 요인이다. CFG 계수가 비트 조건을 과증폭해 그리드 자체보다 더 밀어낸 것이고, 1.5로 낮추면 91.5로 그리드 값에 수렴한다.

## 해결

### 1. 평가 기준을 목표값이 아니라 이론값으로 둔다

조건 합성 코드를 고칠 수 없다면(상류 라이브러리라면) 측정 기준을 바꾸는 것이 맞다. 90.91로 연주한 것은 오차가 아니라 정확한 추종이다.

```python
FRAME_RATE = 50          # sample_rate / 640

def effective_bpm(target_bpm, frame_rate=FRAME_RATE):
    """int() 내림 후 실제로 만들어지는 비트 그리드의 BPM."""
    gap = int(60 / target_bpm * frame_rate)
    return frame_rate / gap * 60

target = 89
theoretical = effective_bpm(target)        # 90.909...
measured = 91.5

print(f"목표 {target}  이론 {theoretical:.2f}  측정 {measured}")
print(f"목표 대비 오차 {(measured/target - 1)*100:+.1f}%")           # +2.8%
print(f"이론 대비 오차 {(measured/theoretical - 1)*100:+.1f}%")      # +0.65%
```

목표 대비로 재면 2.8% 오차지만, 이론값 대비로 재면 0.65%다. **후자가 모델의 추종 성능이고, 전자는 거기에 양자화 오차가 섞인 값이다.** 두 수치를 섞어 쓰면 모델 성능을 잘못 평가한다.

### 2. 격자에 맞는 BPM을 고른다

실험에서 BPM을 자유롭게 정할 수 있다면, 표현 가능한 값을 쓰면 양자화 오차가 0이 된다.

```python
def representable_bpms(lo=60, hi=180, frame_rate=FRAME_RATE):
    out = []
    n = int(frame_rate / hi * 60)
    while True:
        n += 1
        bpm = frame_rate / n * 60
        if bpm < lo:
            break
        if bpm <= hi:
            out.append((n, round(bpm, 2)))
    return out

for n, bpm in representable_bpms(80, 100):
    print(f"gap {n:3d} frames  ->  {bpm:7.2f} BPM")
```

```
gap  30 frames  ->  100.00 BPM
gap  31 frames  ->   96.77 BPM
gap  32 frames  ->   93.75 BPM
gap  33 frames  ->   90.91 BPM
gap  34 frames  ->   88.24 BPM
gap  35 frames  ->   85.71 BPM
gap  36 frames  ->   83.33 BPM
gap  37 frames  ->   81.08 BPM
```

120 BPM(gap 25)처럼 딱 맞는 값이 있는 것은 우연이 아니다. `50/25*60 = 120`이다. 저자 예제가 120을 쓴 이유 중 하나일 수 있다.

### 3. 내림 대신 반올림이 필요하면 상류에서 고친다

`int()`를 `round()`로 바꾸면 89는 gap 34(88.24)를 선택해 오차 방향이 아래로 바뀌고 절대 오차는 작아진다(0.85% vs 2.15%). 다만 상류 수정은 학습 때와 다른 조건 분포를 만들 수 있으므로, 조건 합성 방식을 바꾼 뒤에는 품질을 다시 측정해야 한다.

## 배운 점 / Development Way

조건을 **이산 격자에 올리는 모든 지점에서 표현 가능한 값의 집합을 먼저 확인한다.** 프레임 레이트, 토큰 길이, 홉 크기가 개입하는 곳마다 연속값이 격자로 떨어지고, 그 격자는 보통 문서에 적히지 않는다. 입력과 출력이 미세하게 어긋나면 모델을 의심하기 전에 격자를 계산해 본다. 계산은 한 줄이고 결과는 명확하다.

**지시한 값과 실제 지시가 된 값을 구분한다.** 이 사례의 교훈은 "모델이 조건을 안 따른다"가 아니라 "내가 넣은 값과 모델이 받은 값이 다르다"였다. 조건부 생성에서 성능을 평가할 때 분모를 목표값으로 두면, 전처리 단계의 양자화 오차가 모델 성능으로 계산된다. 평가의 기준점은 **모델이 실제로 받은 조건**이어야 한다.

치우침의 **방향이 일정한지** 본다. 무작위로 흩어지면 추종 실패이고, 한 방향으로 일정하게 쏠리면 계통 오차다. 계통 오차는 코드에 원인이 있고 재현되므로 찾을 수 있다. 측정값 두 개가 모두 목표보다 크고 작은 쪽이 일정했던 것이 `int()`를 들여다보게 한 신호였다.

**버그와 필연을 구분해서 기록한다.** 이 건은 고칠 대상이 아니라 알고 있어야 하는 성질이다. 버그로 기록하면 누군가 상류 코드를 고치려 들고, 모르고 넘기면 평가 기준이 틀어진다. 기록에는 "왜 이렇게 되는가"와 "그래서 무엇을 기준으로 재는가"를 함께 남긴다.
