# MusiConGen에서 30초가 아닌 길이로 생성하면 코드 조건의 prepend 경로가 조용히 무시된다

## 상황

MusiConGen(MusicGen-melody 1.5B 파인튜닝, 코드·비트 조건부 생성)으로 원곡에서 추출한 코드 진행과 BPM을 조건으로 넣어 백킹 트랙을 재생성하는 작업이었다. 생성 길이는 선행 실험 산출물과 맞추려고 15초로 잡았다.

결과물에 잡음이 심해 비트와 코드 진행을 귀로 판별할 수 없었다. 생성 파라미터(`duration`, `extend_stride`, `top_k`, `temperature`, 프롬프트 길이)를 바꿔도 달라지지 않았고, 저자의 공식 설정을 그대로 돌린 대조군에서도 같은 잡음이 나왔다.

## 에러

**에러가 발생하지 않는다.** 예외도, 경고도 없다. 조건이 무시된 채 생성이 끝까지 정상 완료된다.

관측 가능한 유일한 신호는 음질 지표였다. 같은 조건·같은 seed로 길이만 바꿔 측정한 값이다.

```
지표                 15초      30초      변화
spectral flatness    0.06467   0.03765   -41.8%
8kHz+ 에너지 비율    0.2444    0.1792    -26.7%
```

`spectral flatness`는 0에 가까우면 음정 있는 소리, 1에 가까우면 백색잡음이다. 길이만 바꿨는데 잡음 지표가 42% 떨어졌다는 것이 단서였다.

## 원인

`audiocraft/audiocraft/modules/conditioners.py`의 `ConditionFuser.forward`가 **조건 텐서의 길이를 CFG 드롭아웃 판별에 하드코딩**한다.

```python
elif op == 'prepend':
    if cond_type == 'chord':
        cond_prepend = torch.zeros(cond.shape[0], 235, cond.shape[2], device=cond.device)
        if cond.shape[1] == 1500:          # if condition not dropout
            for i in range(235):
                cond_prepend[:, i, :] = cond[:, round(i * (1500/235)), :]
```

주석 `# if condition not dropout`이 의도를 드러낸다. 개발자는 **"조건 길이가 1500이면 진짜 조건, 아니면 드롭아웃된 빈 조건"**으로 판단하는 코드를 썼다.

1500의 출처는 학습 설정에 있다.

```
dataset.segment_duration : 30      # 학습은 항상 30초 조각
frame_rate               : 50.0    # = sample_rate 32000 / 640
→ 30 x 50 = 1500
```

학습 중 조건 길이는 **항상** 1500이었으므로, 그 값을 "드롭아웃 아님"의 판별자로 써도 당시에는 문제가 없었다. 추론 시 사용자가 다른 길이를 넣을 수 있다는 것이 고려되지 않았다.

15초를 넣으면 조건 길이는 750이 된다. `750 != 1500`이므로 실제 조건이 드롭아웃으로 오판되고, prepend 자리에는 `torch.zeros`로 만든 235개의 빈 토큰이 들어간다.

### 더 나쁜 부분 — 두 경로가 어긋난다

실측한 조건 주입 설정은 이렇다.

```python
cond2fuse = {'chord': ['sum', 'prepend'], 'beat': ['sum'], 'description': ['prepend']}
in_attn   = True
```

코드 조건은 `sum`과 `prepend` **두 경로**를 쓴다. 그런데 `sum` 분기에는 같은 길이 검사가 없다.

```python
if op == 'sum':
    cond_sum = cond[:, offsets[0]:offsets[0]+T]
    if cond_sum.shape[1] != 0:            # 길이 0만 확인. 1500 검사 없음
        ...
        input[:, -cond_sum.shape[1]:, :] = input[:, -cond_sum.shape[1]:, :] + cond_sum
```

따라서 15초에서는 코드 조건이 **`sum`으로는 정상 주입되고 `prepend`로만 공백이 들어간다.**

학습 중 모델이 본 조합은 두 가지뿐이다. CFG(Classifier-Free Guidance)를 학습하기 위해 조건을 일부러 빼는 비율이 0.2이므로,

| 상태 | sum 경로 | prepend 경로 | 학습 중 비율 |
|---|---|---|---|
| 정상 | 실제 조건 | 실제 조건(235개로 압축) | 80% |
| 드롭아웃 | 없음(길이 0, 건너뜀) | 공백(zeros) | 20% |

둘 다 **일관성이 있다.** 조건이 있으면 두 경로 모두 있고, 없으면 두 경로 모두 없다.

15초 추론은 **`sum`=실제 조건, `prepend`=공백**이라는 모순된 상태를 만든다. 학습 중 한 번도 나타나지 않은 입력이므로 모델의 동작에 아무 보장이 없다. 게다가 `in_attn=True`라서 `sum`으로 들어온 실제 조건이 attention 층에도 전달되고, 추론 시 `cfg_coef`(기본 3.0)가 그 상태에서 나온 로짓 차이를 3배로 증폭한다.

## 해결

### 1. 조건 주입 경로를 먼저 실측한다

이 설정을 모르면 "코드 조건이 완전히 무시됐다"고 잘못 진단한다. 실제로는 한 경로만 끊긴다.

```python
fuser = model.lm.fuser
print("cond2fuse  :", fuser.cond2fuse)
print("in_attn    :", getattr(fuser, "in_attn", None))
print("frame_rate :", model.frame_rate)
print("expected   :", int(model.frame_rate * 30), "frames for 30s")
```

### 2. 생성 길이를 학습 `segment_duration`에 맞춘다

```python
FRAME_RATE = 50          # = sample_rate 32000 / 640
SEGMENT    = 30          # 학습 config의 dataset.segment_duration

DURATION = SEGMENT       # 다른 값을 쓰면 prepend 조건이 공백이 된다
assert int(FRAME_RATE * DURATION) == 1500, "조건 길이가 1500이 아니면 조건이 무시된다"

model.set_generation_params(duration=DURATION, top_k=250, cfg_coef=1.5)
```

### 3. 길이 스윕을 돌렸다면 결과를 폐기한다

`[10, 15, 20]` 같은 스윕은 **전 구간이 결함 구간**이므로 결과를 해석할 수 없다. 1500프레임이 되는 길이만 비교 대상이다.

### 4. 상류 수정이 필요하면 조건 길이로 판별하지 않게 바꾼다

근본 해결은 드롭아웃 여부를 길이로 추론하지 않는 것이다. 드롭아웃 플래그를 조건과 함께 전달하고, prepend 압축은 실제 길이에 맞춰 리샘플링하면 된다.

```python
# 개념 예시 — 길이에 의존하지 않는 형태
if not is_dropped:                                  # 플래그로 판별
    L = cond.shape[1]
    for i in range(235):
        cond_prepend[:, i, :] = cond[:, round(i * (L / 235)), :]
```

다만 이렇게 바꾸면 학습 때 보지 않은 길이로 추론하게 되므로, **조건이 들어가긴 하지만 품질은 별개로 검증해야 한다.** 조건이 무시되는 것과 분포 밖 길이로 추론하는 것은 다른 문제다.

## 주의사항

**조용한 실패를 길이 가정으로 만들면 사용자가 알 수 없다.** 이 코드는 예외도 경고도 내지 않으므로, 상류 라이브러리를 수정할 수 없는 입장이라면 호출하는 쪽에서 `assert`로 막는 것이 유일한 방어다.

반대로 비슷한 코드를 직접 쓸 일이 있다면, **텐서의 shape으로 의미를 추론하는 분기를 만들지 않는다.** 의미는 플래그로 전달한다. shape 기반 분기는 학습·추론 설정이 같을 때만 성립하고, 그 전제는 문서에 적히지 않은 채 코드에 묻힌다.

## 배운 점 / Development Way

라이브러리에 하드코딩된 숫자를 만나면, 그 숫자를 "마법 상수"로 넘기지 않고 **학습 설정에서 출처를 찾는다.** 1500이 `segment_duration × frame_rate`라는 것을 확인한 순간 두 가지가 동시에 설명됐다. 왜 그렇게 짜도 당시에는 문제가 없었는지, 그리고 언제 깨지는지. 출처를 모르면 "이상한 코드"로만 보이고, 어떤 입력에서 안전한지 판단할 수 없다.

조건이나 입력이 모델에 들어가는 **경로를 먼저 실측한다.** 한 조건이 여러 경로로 들어가는 설계에서는 일부만 끊기는 상태가 생기고, 그게 완전히 끊긴 것보다 진단하기 어렵다. 완전히 끊기면 결과가 명백히 무작위가 되지만, 일부만 끊기면 그럴듯한 결과가 나오면서 품질만 나빠진다. 경로 구성을 출력해 보는 데 드는 비용은 한 줄이고, 모르고 진단하면 잘못된 결론을 글로 남기게 된다.

조건부 생성 모델의 품질 문제를 만나면 **먼저 "조건이 실제로 들어갔는가"를 확인한다.** 모델 성능, 샘플링 파라미터, 프롬프트 표현을 의심하기 전에 조건 주입 자체를 확인하는 것이 순서다. 이 사례에서는 파라미터 가설 다섯 개를 검증하는 데 시간을 쓰고 나서야 조건 쪽을 봤다.

학습 설정과 추론 설정이 **다를 수 있다는 전제를 기본값으로 둔다.** 학습 코드가 한 가지 설정만 가정하고 쓰였다면, 그 가정은 추론 인터페이스에 노출되지 않은 채로 남는다. 오픈소스 모델을 가져다 쓸 때 학습 config를 읽는 것은 성능 재현을 위한 것만이 아니라, 추론에서 밟을 수 있는 지뢰를 찾는 작업이다.

마지막으로, 길이·크기 같은 파라미터를 스윕하기 전에 **그 범위 전체가 유효한지 확인한다.** 유효하지 않은 구간에서 얻은 비교 결과는 틀린 값이 아니라 해석 불가한 값이고, 그걸 모르면 최적값을 찾았다고 믿게 된다.
