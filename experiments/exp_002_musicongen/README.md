# EXP-002 — MusiConGen 파이프라인 (진행 중)

## 목적

BPM·코드를 명시적으로 강제하는 MusiConGen을 재생성 단계에 써서, 원곡과의 타이밍 정렬 문제를 처음부터 줄일 수 있는지 검증.

> **2026-10-30 — 목적이 한 차례 바뀌었다.** 재생성물에 잡음이 심해 비트와 코드 진행을 판별할 수 없었고, 망가진 음원에서 뽑은 수치는 쓸 수 없다고 판단했다. 그래서 타이밍 정렬 검증을 보류하고 **음질 저하 원인 규명**을 먼저 수행했다. 평가 기준을 먼저 세워 둔 덕분에 측정 전에 "측정 가능한 상태인가"를 확인할 수 있었고, 그 확인이 목적 전환의 근거가 됐다.

## 방법

`config.yaml` 참고. 파이프라인 전체 구조는 Notion "02번 노트북 — 재생성/재조합 로직 설계" 페이지의 다이어그램 참고.

### 파이프라인 순서 (PROPOSAL.md 2.3, 4.1)

1. 원곡에서 BPM·코드를 한 번 추출한다 (librosa + BTC-ISMIR2019).
2. MusiConGen으로 BPM·코드 조건부 전체 백킹트랙을 생성한다.
3. 생성된 전체 트랙을 Demucs로 재분리한다.
4. 재분리 결과에서 `target_stem`(예: drums)만 추출한다.

`target_stem`은 생성 조건이 아니라 3단계 재분리 이후의 추출 라벨이다. MusiConGen을 비롯한 MusicGen 계열 모델은 스템 단위 생성을 지원하지 않는다.

> 1단계 도구가 madmom에서 librosa + BTC로 바뀌었다 (2026-10-12). madmom은 제거된 numpy 별칭을 19개 파일 97곳에서 참조해 설치되지 않는다 — `config.yaml` known_issues 참조.

### 평가 지표 — 세 개를 교차로 읽는다

원래 계획한 지표(`bpm_error`, `beat_alignment`, `onset_alignment`, `chord_consistency`)는 음질 때문에 측정이 막혔다. 그 선행 조건으로 음질 자체를 재는 지표를 추가했다.

| 지표 | 의미 | 역할 |
|---|---|---|
| spectral flatness | 스펙트럼의 평평함. 0에 가까우면 음정 있는 소리, 1에 가까우면 백색잡음 | 잡음 총량 |
| 8kHz+ 에너지 비율 | 고역이 전체 에너지에서 차지하는 비중 | "지지직" 계열 잡음. flatness와 독립적인 단서 |
| HPSS 타격음 비율 | 조화음/타격음 분리 후 타격음 쪽 에너지 비중 | **총량과 성분 분포를 구분** |

측정 함수는 [`../../src/audio_metrics.py`](../../src/audio_metrics.py)에 단일 정의로 둔다. 노트북에 복사하지 않는다 — 복사본이 생기면 버전이 갈라지고 과거 측정값과의 비교가 조용히 무효가 된다.

### 기준선 — 절대값은 판단을 만들지 못한다

| 기준선 | flatness | 의미 |
|---|---|---|
| 코덱 왕복 | 0.00451 | 원곡을 EnCodec으로 인코딩 후 디코딩. **이론적 하한선** |
| 원곡 | 0.00679 | 비교 대상 원본 |
| 공식 설정 대조군 | 0.03212 | 저자 기본 설정 그대로. **우리가 추가한 분**을 재는 기준 |

### 가설과 처리

| # | 가설 | 처리 | 방법 |
|---|---|---|---|
| H1~H5 | 생성 길이 / `extend_stride` / `top_k`·`temperature` / description 길이 / 체크포인트 손상 | 기각 | **공식 설정 대조군 1회로 일괄 기각.** 대조군에서도 같은 잡음이 나왔으므로 우리가 바꾼 파라미터는 원인이 아니다 |
| H6 | EnCodec 디코더가 음질을 떨어뜨린다 | 기각 | 원곡 왕복 측정 — flatness 0.00451 < 원곡 0.00679. **코덱 통과가 지표를 오히려 개선** |
| H7 | 조건 주입 경로의 코드 결함 | **확인** | 소스 추적 + 학습 설정 대조 + 길이 전환 실험 |
| H8 | `cfg_coef` 3.0 증폭이 분포 이탈을 악화 | 기각 | 변수 하나만 바꾼 대조 실험 |

H8의 판정 기준은 **측정 전에 고정했다** — flatness 10% 이상 감소면 확인, ±10% 안이면 기각. 결과를 먼저 보면 자기 가설에 유리하게 해석하게 되기 때문이다.

### 결과 1 — 저자 공식 설정도 코덱 대비 7.12배다

측정 범위를 "방금 만든 파일 1개"에서 "전체 6개"로 넓힌 순간 나온 사실이다.

아무것도 바꾸지 않은 실행이 7.12배라는 것은 **잡음의 대부분이 우리가 만든 것이 아니라 이 체크포인트가 32kHz에서 내는 소리의 기본 특성**이라는 뜻이다. 이 기준선이 생긴 뒤 수사 방향이 "우리가 무엇을 잘못 넣었나"에서 "우리 기여분 1.17배가 어디서 오나"로 좁혀졌다.

### 결과 2 — `ConditionFuser.prepend`의 하드코딩 (H7 확인)

`audiocraft/audiocraft/modules/conditioners.py`, `ConditionFuser.forward`:

```python
elif op == 'prepend':
    if cond_type == 'chord':
        cond_prepend = torch.zeros(cond.shape[0], 235, cond.shape[2], device=cond.device)
        if cond.shape[1] == 1500:          # if condition not dropout
            for i in range(235):
                cond_prepend[:, i, :] = cond[:, round(i * (1500/235)), :]
```

**1500의 출처**를 학습 설정에서 확인했다: `dataset.segment_duration: 30` × `frame_rate: 50` = 1500. 학습 중 조건 길이는 항상 1500이었으므로 이 상수를 "드롭아웃 아님"의 판별자로 써도 당시에는 문제가 없었다. 추론 시 다른 길이가 들어올 수 있다는 것이 고려되지 않았다.

15초 = 750프레임 → `750 != 1500` → "드롭아웃된 조건"으로 오판 → prepend에 0 텐서 235개.

실측 설정은 `cond2fuse = {'chord': ['sum','prepend'], 'beat': ['sum'], 'description': ['prepend']}`, `in_attn=True`다. `sum` 분기에는 같은 검사가 없으므로 코드 조건은 **sum으로는 정상 주입되고 prepend로만 공백**이 들어간다.

| 상태 | sum 경로 | prepend 경로 | 학습 중 출현 |
|---|---|---|---|
| 정상 학습 | 실제 조건 | 실제 조건 (235 압축) | 80% |
| CFG 드롭아웃 | 없음 (길이 0, 건너뜀) | 공백 (zeros) | 20% |
| **우리 15초** | **실제 조건 (750)** | **공백 (zeros)** | **0% — 분포 밖** |

학습 중 두 경로는 항상 일관됐다. 15초에서 처음으로 모순된 조합이 만들어졌고, `cfg_coef` 3.0이 그 상태에서 나온 로짓 차이를 3배로 증폭한다.

**검증** — 30초(= 정확히 1500프레임)로 전환:

| 지표 | 15초 | 30초 | 변화 |
|---|---|---|---|
| flatness | 0.06467 | 0.03765 | **−41.8%** |
| 8kHz+ | 0.2444 | 0.1792 | **−26.7%** |
| ×대조군 | 2.01 | 1.17 | 1.7배 기여분 제거 |

### 결과 3 — H8 기각, 그러나 부수 성과 두 개

변경한 것은 `cfg_coef` 3.0 → 1.5 **하나뿐**이다 (duration 30, seed 42, meter 4, 코드 11마디, BPM 89, 동일 프롬프트 전부 동일).

| 지표 | cfg 3.0 | cfg 1.5 | 변화 |
|---|---|---|---|
| flatness | 0.03765 | 0.03842 | +2.0% |
| 8kHz+ | 0.1792 | 0.1801 | +0.5% |
| 타격음 비율 | 0.209 | **0.131** | **−37.3%** |
| BPM (목표 89) | 96.2 | **91.5** | 오차 5.8% → **0.65%** |

사전 기준대로 **기각**.

**부수 성과 ① — 청취 인상과 지표의 불일치를 설명했다.** 청취 보고는 "멜로디가 더 명확해졌다, 잡음은 여전하다"였다. 잡음 총량은 그대로이고 타격음 비중만 37% 떨어졌다. 타격음이 줄면 조화음(멜로디) 비중이 자동으로 올라간다. **잡음이 줄어든 것이 아니라 분포가 바뀐 것이다.** 지표가 하나였다면 flatness만으로 "변화 없음", 타격음 비율만으로 "37% 개선"으로 각각 오판했다.

**부수 성과 ② — 템포 정확도 9배 개선.** `beat_gap = int(60/89*50) = int(33.70) = 33` → 실효 BPM은 50/33×60 = **90.91**이다. 정수 내림에서 오는 구조적 오차다. cfg 3.0은 이론값 대비 +5.8%, cfg 1.5는 +0.65%. cfg 3.0이 비트 조건을 과증폭해 템포를 밀어내고 있었다.

### 원인의 3층 분리

| 층 | 기여 | 성격 | 대응 |
|---|---|---|---|
| ① 체크포인트 고유 잡음 | 코덱 대비 5.3~7.1배 | MusiConGen 1.5B 특성 | 통제 밖. 모델 교체 외 수단 없음 |
| ② `ConditionFuser` 결함 | 추가 약 1.7배 | 코드 결함 | **해결** — `duration_sec: 30` 고정 |
| ③ 조건 주입 초과분 | 추가 1.17배 | `sum` 경로 추정 | 후속 검증 항목 |

**"전부 해결"이 아니다.** 통제 가능한 부분과 불가능한 부분의 경계를 숫자로 그었고, 통제 가능한 부분은 제거했다.

### 확정 설정

| 항목 | 값 | 근거 |
|---|---|---|
| `duration_sec` | **30** (고정) | 1500프레임이어야 prepend가 동작. 15초는 쓰지 않는다 |
| `cfg_coef` | **1.5** | 잡음에는 무효하지만 템포 오차를 9배 줄인다 |
| `hint_bpm` | 필수 | 생략 시 librosa 옥타브 오류 |

### 원래 목적에 대한 답 — 보류

타이밍 정렬 검증(`bpm_error`, `beat_alignment`, `onset_alignment`, `chord_consistency`)은 **아직 하지 못했다.** ①층이 남아 있어 판별 신뢰도를 확보하지 못했다. 이 지표를 측정하려면 ③층을 제거하거나 모델을 교체해야 한다.

**EXP-003(MusicGen-Melody/Style)에서 ①층이 더 낮은지 비교하는 것이 다음 분기점이다.** 원곡 오디오를 직접 참조하는 모델이므로 ①층 자체가 다를 수 있다.

### 후속 검증 항목 — ③층

조건별 `output_proj` 가중치 분포:

| 조건 | std | absmax |
|---|---|---|
| `description` | 0.01264 | — |
| `chord` | 0.02915 | — |
| **`beat`** | **0.56999** | **1.0** |

약 50배 차이다. beat 입력값은 최대 1.9까지 가고, 이 값이 오디오 토큰 임베딩에 직접 가산된다. 작은 값들 사이에 큰 값을 더하면 원래 정보가 묻힌다.

**검증 방법**: forward hook으로 `sum` 경로의 가산 전후 텐서 크기를 실측해, beat 조건이 토큰 임베딩 분포를 얼마나 밀어내는지 확인한다.

### 이 실험에서 얻은 방법론

1. **측정 전에 "측정 가능한 상태인가"를 확인한다.** 망가진 입력에서 뽑은 수치는 쓸 수 없다
2. **기준선 없는 절대값은 판단을 만들지 못한다.** 코덱 왕복과 공식 대조군이 없었다면 ①과 ②를 분리할 수 없었다
3. **판정 기준은 측정 전에 적는다.** 결과를 먼저 보면 자기 가설에 유리하게 해석한다
4. **지표는 복수로, 교차로 읽는다.** 하나만 보면 반대 결론도 나온다
5. **측정 범위를 넓혀본다.** 파일 1개 → 6개로 넓혔더니 가장 중요한 사실이 나왔다
6. **변수는 하나씩 바꾼다.** 둘을 동시에 바꾸면 인과를 가릴 수 없다
7. **개별 가설을 검증하기 전에 "전부 아님"을 한 번에 보일 방법을 찾는다.** 대조군 1회가 가설 5개를 기각했다
8. **못 잡은 것은 근거와 검증 방법을 적어 남긴다.** 그러면 미완이 아니라 백로그가 된다
9. **라이브러리의 하드코딩된 상수는 학습 설정에서 출처를 찾는다.** 1500의 출처(`segment_duration` × `frame_rate`)를 확인한 것이 "왜 그렇게 짰는지"와 "언제 깨지는지"를 동시에 설명했다
